# Bring the Rust Raft ledger to production readiness

The [candidate qualification report](release-qualification.md) records the local results and open deployment gates.

Deliver a release candidate that a backend team can integrate, an operator can recover, and a reviewer can qualify for a stated workload. Implement the fixes, measure their effect, and provide a release decision for the intended deployment.

Start with `docs/project-record.md`, `ARCHITECTURE.md`, `output/pdf/ledger-engineering-assessment.pdf`, and the linked measurements. Recheck each finding against the current source. Track each one through its fix and test, a verified existing resolution, or an explicit release decision. Continue independent engineering work while product decisions or infrastructure are pending.

1. **Define the launch contract.** Agree with the owner on the deployment mode, peak workload, sustained throughput, p99 payment latency, acceptable data loss, recovery time, and time allowed to restore three healthy voters. Set these targets before tuning. Keep both supported modes correct. Synchronous protection must recover every acknowledged acceptance and rejection from a surviving independent journal and pause protected replies when journal coverage is unavailable. Learner mode must keep serving with a voting majority during export outages. In a total-loss drill, compare independent client receipts with the restored archive to measure any acknowledged work lost.

2. **Prove financial and distributed correctness.** Test quorum loss, leader changes, crashes, current reads, and timeouts followed by same-ID retries. Reconcile balances, postings, original decisions, conflicting ID reuse, ordered funding allocations, and partially captured holds against an independent model. Replay older histories through upgrades. Verify the learner never votes, generation changes isolate the old majority, and restored state agrees with client receipts through the promised recovery point.

3. **Make recovery dependable.** Diagnose the follower-start journal-lock timeout under sustained writes. Exercise oversized Raft appends, checkpoint stalls, slow or interrupted snapshot transfer, damaged recovery bases, pinned history, and abandoned restore files. Implement and rehearse a supported blank-disk voter replacement or bounded-interruption recovery procedure. On separate hosts with independent storage, measure time to the first successful payment and time to three healthy voting disks. Verify independent archive and Kafka progress, archive-before-publication when both are enabled, duplicate delivery, multi-broker failover, and reconciliation of Kafka-only events beyond the restore point.

4. **Improve measured performance.** Establish a reproducible baseline for each mode, profile the limiting path, implement improvements, and run at least three matched release-build trials before and after each retained optimization. Include hot and cold accounts, actual client retries, overload, compaction, and catch-up during writes. Report offered and completed work, new decisions, postings, rejections, retries, sender drops, p50/p95/p99 latency, archive lag, and peak disk use. Run a sustained storage-growth test and the outstanding 1 TB recovery drill before claiming that scale.

5. **Improve the code and the product interface.** Keep crate ownership clear. Centralize service-mode policy across startup, reads, and replies. Separate node admission from startup where it simplifies maintenance, and make Kafka optional in voter-only builds. Ship authenticated voter health, peer progress and export lag, distinct errors for temporary overload and oversized requests, a remaining-hold lookup, and a runnable first payment with same-ID retry. Verify caller permissions for sensitive operations and document backup, restore, upgrade, and rollback.

**Completion requires** reproducible builds, formatting and strict Clippy checks, passing workspace and relevant opt-in tests, compatibility fixtures, and a release report linking every reviewed finding to evidence. Include the tested revision or source fingerprint, commands, environment, raw results, before-and-after measurements, and runbooks. Demonstrate the agreed throughput, latency, and recovery targets with the promised durability enabled. Give a go/no-go decision for each claimed deployment and scale. For any unmet gate, name the blocker, its consequence, and the exact test or owner decision needed to close it.
