# RFC 0020 — Publish committed decisions to a broker

## Problem

Backend consumers need to know which payments posted, which requests were rejected and how a waterfall actually allocated funds. A command observed by the leader before commitment can still disappear. An entry can also contain several commands or a retry of an earlier one.

## Proposed solution

Read the learner's ordered decision history by Raft index and original command slot. Emit one logical event per first durable request decision, including business rejections. An identical retry or conflicting reuse of the request ID leaves the original decision in place. Malformed RPCs and Raft election entries produce no business event. The envelope carries the original typed command, outcome, ledger definition, generation and position. Posted entries carry the resolved lines. Consumers can deduplicate using the stable decimal key `<ledger_id>/<request_id>` across retries and recovery of the same ledger lineage.

With both adapters enabled, publish only through the confirmed archive and the learner's applied position. With the no-op archive and a real publisher, the applied position alone gates publishing. Adding or replacing the archive keeps the existing broker cursor. Further events wait until the new archive covers their positions. An event delivered earlier under applied-only policy keeps that original guarantee. With the no-op publisher, the archive continues and there is no delivery cursor. A broker outage pauses publication while the independent archive worker can advance.

The Kafka adapter uses Rust’s `rdkafka` crate with librdkafka and encodes events with `prost`. It writes versioned Protobuf records to one explicitly configured partition per ledger, using an idempotent producer, `acks=all` and delivery reports. Create the topic and partition first. The local cursor advances only after the entire ordered page is confirmed. A crash after delivery and before syncing the cursor can replay a page. Kafka offsets identify physical records. Consumers should store the event ID atomically with their own side effect. A new destination receives its own cursor and can backfill from the beginning. The Kafka destination identity includes the configured bootstrap address set, topic name and partition. Changing them can backfill history to the same physical broker under a new cursor. Recreating a topic at the same address and name retains the saved cursor. Use a new destination or a deliberate replay from fresh cursor storage to repopulate an empty topic. A replacement ledger generation needs a deliberate replay decision.

## Tradeoffs

Delivery is at least once. Duplicate positions can appear after newer positions on retry. First occurrences retain their order for an uninterrupted ledger lineage. One fixed partition keeps the ledger ordered and bounds publishing throughput. The first adapter waits for each delivery report. Different ledgers can use different partitions, and consumers can scale independently. Broker replication factor, minimum in-sync replicas, message-size limits and retention remain topic deployment settings. Configure message limits to admit the largest decision in use. In applied-only mode a broker can retain decisions beyond a later disaster restore cut. Reconcile those old-generation events against the authoritative cut before resuming downstream side effects. Retrying a request lost from the recovered ledger can produce a different business decision under the same ID. The broker lacks the raw consensus history required for restore.
