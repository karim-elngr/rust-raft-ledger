# Recovery operations

Use this procedure for permanent loss of a voter disk or loss of an entire generation. A fixed roster needs a new generation to replace a blank voting disk. If the original voter disk is intact, restart it with the same configuration and inspect its applied index as it catches up. Two surviving voters can continue to serve, with no spare vote. An operator can stage the replacement hosts and configuration while those voters serve.

## Before a failure

- Place each voter disk on independent durable storage. Keep the synchronous POSIX journal or learner POSIX archive on a separate failure domain. Verify the expected volume identity on **each** host before initialization or restore. Provision the mount and journal parent directory first. `journal-init` can create the final path component or use an empty mounted directory. A missing mount that exposes an ordinary local directory can create a journal on the wrong device. The path-separation check detects overlapping trees and resolved aliases. It cannot identify a device's failure domain.
- The journal requires cross-host advisory locks, same-directory atomic rename, immutable file publication and durable file and directory sync. Configure the storage service and mount to bound I/O stalls. The two-second journal deadline bounds lock acquisition only. Check durability after power loss and arbitration across the actual hosts and storage service before approving a deployment.
- Back up the whole journal directory as one storage-consistent image, including `HEAD`, `BASE`, immutable objects, `recovery-images-v1`, and its pin registry. Check the ledger definition and generation. Preserve independent client receipts by ledger ID, request ID, original payload and complete outcome, including declines and allocation lines. For a rehearsal, give the administrative configurations a private writable copy of the backup, fresh disposable data directories and isolated endpoints. Verify the configured journal path, then scrub and fence that copy, restore it, and reconcile the receipts. Keep the rehearsal isolated from production peer, archive and broker endpoints. Handle a payment timeout by retrying its original payload under its original ID.
- While live, `ledger-node journal-checkpoint SOURCE.toml` builds or refreshes an image from verified history. Budget disk space for the old image, new image, private build databases, and each restore. A stopped voter's `reclaim` can make its older raw history depend on the exact image that voter pinned. Keep that image and the pin registry accessible even when the voter is offline. `checkpoint-scrub` checks local sealed state. `journal-scrub` checks segments from genesis. A successful restore exercises both the published image and its tail.

### Check the shared journal mount

On each intended host, build the probe with `cargo build --locked -p ledger-recovery --example journal_mount_probe`. Use the ledger service account and the same storage service, mount options and network route as the deployment. Supply an existing scratch directory on that volume, outside any journal. Confirm its mount identity first. The holder creates a unique disposable child and prints a run ID.

```sh
# Host A, left running while the observer starts
target/debug/examples/journal_mount_probe holder /mnt/site-journal/qualification-scratch

# Host B, using its mount path for that same scratch directory and A's run ID
target/debug/examples/journal_mount_probe observer /mnt/site-journal/qualification-scratch RUN_ID
```

Save both transcripts and exit codes. Require both to succeed, then exchange host roles. The observer must time out on the live holder's lock, verify the checksum-bound journal head and replay the expected entries at indexes 16 and 32. It then publishes entry 33 for the holder to verify. Either endpoint may have multiple successful observations of the same head. Each handshake allows five minutes. The probe leaves its own child directory for inspection. The local drill exercised two processes on one mount. Power-loss durability requires a separate interruption and cold-remount exercise on the intended storage. ## Replace disks with a service interruption

Set a maximum interruption and recovery point with the service owner before the drill. Start a monotonic timer when client traffic is quiesced or becomes unavailable. Prepare fresh TLS identities, endpoints, storage and deployment commands in advance. Record the timestamp and cut for each numbered step. If a recovery target is exceeded, escalate to the service owner while keeping the old generation isolated. A measured interruption on a small local fixture supplies no upper bound on a deployment.

1. **Establish the cut.** Quiesce new submissions, resolve uncertain calls by original ID where possible, and save external receipts. For planned learner replacement, let a healthy learner apply through the final committed index. Observe its authenticated `verified_archive_index` reach that cut and run `journal-scrub`. A saved local export cursor alone cannot prove current archive coverage. If loss has already occurred, use the verified archive cut and enumerate outstanding receipts. With no surviving independent archive or journal, this procedure cannot recreate lost voter histories.
2. **Isolate the predecessor.** Stop the old processes, disable their automatic restart, remove old API routes and prevent the old voters from forming a majority or accepting clients. Record the operator's isolation evidence. In learner mode this is essential even if the archive is fenced. `ledger-node fence OLD-ADMIN.toml` performs a compare-and-set. If it loses to a publisher, inspect `journal-head` and retry on the current head. Record the fenced generation, index, term and digest. Keep the old disks and backups intact throughout qualification.
3. **Restore a fresh group.** Configure the same ledger ID, asset and scale, a fresh nonzero generation ID absent from the history, one fixed roster, distinct peer identities, and empty or absent data directories. For learner mode include its learner ID and use the same fenced POSIX archive on each offline administrative configuration. Run `ledger-node restore NEW-MEMBER.toml` on every replacement disk, including the learner when configured. Confirm the same fenced cut for all. If the optional recovery image is damaged, use `restore-from-journal` with intact complete journal history. It authenticates every segment from genesis. Investigate any differing bytes, missing history or generation error before activation.
4. **Verify and activate.** To inspect financial records before activation, reopen a disposable copy of a restored disk offline and use `Replica::decision`, `Replica::account`, `Replica::entry` and `Replica::reservation`. The recovery CLI reports indexes and replay work. Operators using the public API should perform the financial checks in step 5 after activation while ordinary client traffic is still isolated. A complete `journal-scrub` is available if every segment survives. Run `ledger-node activate NEW-VOTER.toml` once on a restored voter. Check `journal-head` for the fresh, active generation at the fenced index and term. An uncertain activation result requires inspecting that head before retrying. Keep the old group isolated after activation.
5. **Return service.** Launch the new members with their run configurations. Learner-mode run configurations omit `recovery_dir`. The learner configures POSIX export under `[export.archive]`. Confirm the elected leader, generation and term with authenticated status. Resolve the recorded IDs and compare the original decisions, balances, posting lines, open holds and remaining allocations through the recovery cut. Issue one small approved payment with a fresh ID. Record elapsed time to this successful payment. Wait for **three distinct voting disks** to report the new generation, common leader, and an applied index covering that payment. Record this second elapsed time and the leader's corresponding peer matches. Resume routed traffic after the owner's release checks pass.
6. **Reconcile downstream effects.** Compare each client receipt and each Kafka event to the restored original decision by ledger ID and request ID. Compare the full decision, amounts and posting lines. Partition/offset alone cannot identify a business effect. Exact duplicate event IDs reuse the consumer's recorded result. Quarantine missing or conflicting decisions and pause the affected side effects until the payments owner reconciles them. A Kafka-only event after the archive cut can describe economic activity absent from the recovered ledger. Obtain independent settlement evidence before any corrective posting and give it its own authorization and request ID. Record accepted and rejected losses separately.

## Repair and interrupted work

`journal-checkpoint-from-journal SOURCE.toml` takes a fresh active nonempty head, authenticates and replays the entire immutable journal, and installs a newly sealed recovery image with a compare-and-set on the observed `BASE` bytes. It can repair a damaged image, binding or bounded regular `BASE` file. A racing head before the initial sample or a racing pointer publication can return a conflict. Retry on a fresh head. If publication continually outruns this first check, briefly quiesce writes until the builder has sampled its cut. The process checks generation and fence ownership at publication. For a fenced disaster, complete `restore-from-journal` and activation first, then repair in the active generation. Oversized pointer files, unreadable storage, or corrupt immutable journal history require verified independent backup material. Preserve damaged content for investigation. Repair publishes a new image, and existing pins still reference their original image. A voter with unreadable pinned history needs the replacement procedure or recovery of that original image from a verified backup.

Restore owns a small, persistent `.ledger-restore-v1-*` directory beside each destination. Its marker binds the destination name and ledger definition. A file lock excludes concurrent restores to that same destination. Repeating restore after interruption reclaims recognized private work and rebuilds against the current fence. A successful publication leaves only the small marker. Unknown files, symlinks, and unverifiable checkpoint contents can stop automatic cleanup. Stop all restore processes and preserve the workspace for inspection before moving it aside and retrying. A power loss during creation of the small marker may require this same procedure. Legacy random `.ledger-restore-*` directories have no destination-bound marker. Keep them until an operator verifies the configured destination, absent live users and a complete replacement or independent backup. Never infer ownership from their names alone.

A returning protected voter reads the atomically published `HEAD` and its immutable object at open. The verifier checks the observed generation before joining. Every protected confirmation still acquires `LOCK`, checks authoritative coverage and syncs the directory as required. To diagnose a stall, set `LEDGER_JOURNAL_LOCK_TRACE=1` on relevant processes and collect stderr with host and wall-clock timestamps. Lines report PID, operation and microseconds spent waiting and holding the lock. Timeouts report the waiting PID and operation. Writers publish a segment and update `HEAD` under the lock. Match long holds with host I/O latency. Trace values from one process cannot identify a dead host's lock holder. The historical timeout transcript identified the waiter at follower open but contained no holder trace.

## Reconcile independent client receipts

Capture the complete original `ledger.v1.Decision` at acknowledgment, including business declines, on storage independent of the replicas and the recovery source. Maintain a durable inventory of acknowledged request IDs at capture time. Preserve a consistent cut of both inventory and files that can be recovered after a crash. An inventory constructed later from the surviving files cannot reveal receipts lost together with their filenames. Verify the inventory’s provenance and the backup’s integrity before running the comparison.

Use a read-only copy of that cut. For ledger 7 put `request-ids.txt` at `/receipts/7/request-ids.txt` and the receipt for request 100 at `/receipts/7/100`. The inventory is a nonempty text file with one canonical decimal unsigned 128-bit ID per line. Use unique IDs and exact decimal filenames, including `0` where applicable. Place only the inventory and its regular receipt files in that ledger directory. Each file contains one unframed protobuf v1 `Decision`, as emitted by Prost’s `encode_to_vec()`, up to the API’s 1 MiB limit. The checker accepts equivalent field orderings. Unknown fields, redundant encodings such as repeated oneof alternatives, incomplete decisions and a reuse response containing `ID_CONFLICT` require investigation. Keep the original command payload and any settlement evidence separately.

Confirm the replacement generation with authenticated member status. Isolate ordinary traffic while checking the cut. Supply voter **client** endpoints and credentials authorized for financial reads. The executable performs one quorum-confirmed `GetRequestOutcome` lookup per valid receipt with a ten-second deadline per ID. Each read observes its own point in time.

```sh
cargo build --locked --release -p ledger-api --example reconcile_receipts
target/release/examples/reconcile_receipts 7 /receipts \
  /tls/voter-ca.pem /tls/reconciliation.pem /tls/reconciliation.key \
  '11,https://voter11.example:9400,voter11.example' \
  '12,https://voter12.example:9400,voter12.example' \
  '13,https://voter13.example:9400,voter13.example'
```

Exit 0 requires every inventoried receipt to match the full v1 decision, including posted entry IDs, ordered lines, amounts, and rejection codes and contexts. Exit 1 identifies per-request discrepancies. A successful lookup with no decision counts as a missing acceptance or missing rejection according to the saved receipt. A different decision counts as a mismatch. An RPC or transport failure leaves that ID **unverified**. A missing or unreadable local file and a malformed receipt count as invalid evidence. Exit 2 means the tool could not begin the comparison, for example because the inventory was empty, ambiguous or inconsistent with the filenames, or the client configuration failed. The comparison relies on the trusted original evidence. The public response contains neither the original command payload nor the generation. The checker only reads outcomes.

To exercise the executable against the local four-member restored generation, set `LEDGER_RECONCILE_BIN="$PWD/target/release/examples/reconcile_receipts"` when running the release `learner_cli_archives` command below. The six-ID run found four matches, one missing acceptance and one missing rejection. The four-ID positive control passed. Additional controls exercised a changed posting, missing and malformed files, an empty inventory, and a failed RPC. [Executable drill transcript](measurements/rc-local/receipt-reconciliation.log)

## Local drill commands

Use the locked workspace with the build prerequisites documented in the README. The network tests require local TCP listeners. The learner drill uses the default Kafka feature and a local librdkafka mock broker unless `LEDGER_TEST_KAFKA_BROKERS` is set.

```sh
cargo test --locked -p ledger-recovery
cargo test --locked -p ledger-replica --lib
cargo test --locked -p ledger-node --test recovery_admin
cargo test --locked --release -p ledger-node --test network total_voter_disk_loss -- --nocapture
cargo test --locked --release -p ledger-node --test network learner_cli_archives -- --nocapture
LEDGER_CANDIDATE_NODE_BIN="$PWD/output/release/ledger-node-macos-arm64" \
  cargo test --locked --release -p ledger-node --test network protected_all_voter_processes_sigkill -- --ignored --nocapture
cargo test --locked --release -p ledger-node --test network learner_process_crash_restores -- --ignored --nocapture
```

The protected drill stops all predecessor voters, removes the old disk tree, restores three blank directories, compares nine separately recorded client receipts on each disk, elects a leader and completes the remaining hold capture. Its timing includes orderly shutdown, creating local replacement directories, fence, restore, activation, election and receipt checks. The learner drill preserves six externally recorded receipts and compares the Kafka-only decisions beyond the archive cut against them. It destroys the old replica disk tree, restores all four fresh disks through the CLI, reconciles every receipt on each disk, activates the replacement generation, elects a quorum leader and posts a fresh payment. The three-voter observation checks each member’s authenticated status through that payment. The restored learner also resumes archive export. Both fixtures share the local host and filesystem. Production RPO, time to first payment and time to three healthy voters require repeated drills on the intended independent hosts, disks, backup service and dataset, including the 1 TB case.
