# Stage an upgrade or roll it back

Keep the executable, lockfile, configuration, certificate set, service mode and generation used by each member. Preserve independently recorded client receipts. Test the exact old and new binaries against copies of the deployment's data, including a checkpoint, its committed tail and any pinned journal image. The checked-in fixture exercises an old protected journal with a partially captured hold and a rejection. A site's own images can include different options and log histories.

1. Take a storage-consistent backup of the independent journal and verify a restore with a private copy of the journal, fresh voter paths and isolated configuration. Point every fence, restore and activate command in the rehearsal at that private journal copy. Keep the production journal, peers, clients and Kafka destination unreachable from the rehearsal. Record the current generation, voter identities, leader, applied indexes, learner/archive/broker progress when applicable, a known receipt and an account balance. Reconcile that baseline. For a learner deployment, decide how much acknowledged work may sit beyond the last independently verified backup.
2. Establish a common committed cut before each restart. For members with the candidate monitor, query each endpoint directly with the operator certificate. Check generation, leader and term. Require the leader's peer match indexes and each voter's own applied index to reach the sampled cut. For members running the original binary, use the legacy verification procedure below. Make a fresh current read and same-ID retry through the normal client.
3. For a compatible binary update, stop one follower cleanly, retain its data tree, deploy the candidate and run it with the same live configuration. Verify term, leader, mode, current reads, original outcomes and convergence before touching the next voter. Repeat with the second follower. Replace the leader last and verify a new election, a fresh payment and its retry. Update the learner separately, verify both destination cursors, and allow for duplicate consumer delivery.
4. Stage API changes after compatible nodes are serving. New RPCs on an old seed may return UNIMPLEMENTED. Updated clients must handle both fixed size refusal and temporary admission refusal during transition. Before using account-admin pins, isolate account administration from ordinary application traffic and drain older voters that do not enforce the policy. Install the same policy on each voter. Save legacy-compatible configuration separately. Keep the topic, partition, cursor and ledger identity consistent.
5. If a replacement follower fails before traffic moves, keep the healthy majority online. To roll that follower back in place, first demonstrate the previous binary can open a copy of the resulting disk and the current journal and can replay the new committed entries without changing outcomes. Restore its compatible configuration and repeat the convergence checks. An older binary can reject new config fields or grant broader permissions. Keep the relevant access restrictions outside it before serving.
6. If downgrade compatibility has not been demonstrated, stop the rollout and retain the functioning majority. Use the bounded-interruption recovery procedure with a compatible build if continuing service requires a new generation. Quiesce and isolate the old majority and reconcile the independent recovery cut with client receipts before reopening. Rewinding individual voting disks, rolling back a live journal HEAD, or restoring an old consumer cursor can lose decisions, invalidate votes or repeat external effects.

## Verify progress on legacy voters

The original standalone binary predates `Monitor/GetStatus`. A direct authenticated `GetRequestOutcome` can return the original decision on the leader or a `ledger-leader-id` redirect on a follower. The redirect establishes responsiveness and identifies a leader known to that follower. It carries no local applied or matched index.

If the running deployment already exports the original embedded `NodeHandle::status()`, collect the local applied indexes and the leader's peer matches from that telemetry. For an ordinary legacy CLI deployment, a protected group can instead verify a **recoverable committed prefix on each disk** while writes are quiesced.

1. Pause new writes, drain accepted calls, and resolve uncertain requests. Use `ledger-node journal-head OLD-ADMIN.toml` to record a verified active journal generation, term and index. Keep this fixed index as the comparison cut.
2. Take a storage-consistent snapshot of each voter's complete data directory and of the independent journal. Mount private writable clones on an isolated host. Make each clone configuration identify its original voter, roster, ledger and generation, with its data directory on the clone. For a reclaimed voter, make the recorded absolute journal mount path resolve to the **private cloned journal and pins**. Keep production storage and peer endpoints inaccessible from this host.
3. On each clone, run the **baseline** binary's `checkpoint CLONE-N.toml` and then `checkpoint-scrub CLONE-N.toml`. Reopening the cloned voter replays its locally committed tail. Require both commands to succeed and record a sealed index at or above the fixed cut for each of the three disks. Leave a lagging voter online and repeat with a later storage snapshot. Run neither clone command against a live voter directory. [Frozen baseline source](measurements/rc-local/source-before.tar.gz) · [Checkpoint and replay contract](rfcs/0012-incremental-snapshots.md)

This procedure verifies per-disk recoverability through the cut. For an acceptance criterion requiring the **live** applied index of every legacy voter, obtain deployment telemetry before proceeding. An installation without that telemetry or storage-consistent snapshots needs a separately rehearsed maintenance procedure. A learner deployment without synchronous protection also needs its own committed cut from trusted Raft telemetry or a separately verified archive and receipt reconciliation. Do not infer the voting cut from a broker cursor.

An upgrade of the binary and a change of topology have different recovery requirements. A topology change uses fresh directories and a new isolated generation. The production binaries and their mixed-version handshake must pass a deployment rehearsal before a rolling update is approved.
